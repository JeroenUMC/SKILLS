# Implement Milestone Orchestrator

Run this skill only when the user explicitly invokes `/orchestrator-implement-milestone`.

## Invocation

- New run: `/orchestrator-implement-milestone <milestone-number>`
- Resume: `/orchestrator-implement-milestone <milestone-number> resume <run-id>`

Use `gh` against the current repository. Read repository instructions before acting. The current local subagent runtime is the execution backend; model assignments are recorded metadata until explicit runtime model routing is available. Do not claim that a Copilot model was used when it was not enforceable.

## Safety and authority

- Never merge pull requests, close issues, release, change project fields, or run destructive Git commands.
- Code changes, commits, pushes, draft PR creation, workflow labels, and concise issue comments are allowed after approval.
- Do not infer dependencies from issue prose or ordinary issue references. Use GitHub's native blocking relationships only. If the available `gh` API cannot expose those relationships, stop planning and report the limitation rather than guessing.
- Use one worktree and branch per issue: `agent/issue-<number>-<slug>`, based on `main`.
- Skip and report issues with an existing open PR or existing agent branch.

## New run

1. Verify the milestone number, repository, default branch, clean enough local state, `gh` authentication, and required repository instructions.
2. Discover the canonical `ready-for-agent` and `ready-for-human` labels. `ready-for-agent` is manually managed and must never be created by this workflow. Create missing `agent/*` status labels automatically when needed.
3. Select open milestone issues carrying `ready-for-agent`.
   - If the label does not exist, ask whether to process all open issues in the milestone.
   - If the label exists but matches no open issues, report an intentional empty scope and stop.
   - Include open `ready-for-human` issues in the dependency graph even though they are never delegated.
4. Fetch native blocking relationships for every relevant issue, including blockers outside the milestone. Detect cycles. A `ready-for-human` issue is a first-class blocker: leave it paused and do not attempt it.
5. Inspect each candidate for refinement risks before planning execution. If an issue combines human/domain decisions with implementation, or is larger than a coherent small vertical slice, propose a human-owned prerequisite and/or implementation split. Present the split for approval rather than silently rewriting issues.
6. Classify blockers explicitly as `native-open-blocker`, `human-decision-required`, `closed-prerequisite`, `external-access`, `cycle`, `existing-work`, or `underspecified`. Closed prerequisites are historical context only; missing ancestry alone is not a blocker.
7. Build a complete dependency plan. Group eligible issues into executable waves; independent issues in one wave may run in parallel. Pause issues blocked by open blockers, human decisions, cycles, non-agent work, skipped existing work, or unresolved prerequisites.
8. For every executable issue, recommend models independently for research, implementation, verification, and review. Validate names against `C:\Users\Z768180\.claude\agent-models.json` if present. These are recommendations and require user approval; the current runtime may not enforce them.
9. Create `.agent-runs/<milestone-number>/<run-id>/plan.md` and `state.json` in the target repository. Ensure `.agent-runs/` is gitignored without overwriting existing user changes. Never put credentials in state.
10. Present the full plan, waves, blockers, refinement splits, skipped work, model recommendations, and approval choices. Do not spawn issue orchestrators until the user approves the plan and model assignments.

## Wave execution

1. Ask for explicit approval of the next executable wave. Approved wave work runs unattended except for defined blockers.
2. Create isolated worktrees and spawn one issue orchestrator per issue. Spawn issues in the same wave in parallel; do not spawn later waves early.
3. The milestone orchestrator is the sole writer of authoritative `state.json`. Issue orchestrators return structured reports and must not concurrently edit shared state. Persist state after every issue transition and record branch, worktree, subagent reports, tests, PR URL, status transitions, and failure diagnostics.
4. Add appropriate `agent/*` labels and concise comments. Comments generated by this workflow must begin with `> *This was generated by AI during orchestration.*`.
5. At wave completion, report successful draft PRs, paused issues, failures, and newly unblocked `ready-for-human` issues. Preserve paused/failed worktrees with the blocker and resume condition; remove successful/completed worktrees only after their report is persisted. Stop and wait for a new explicit resume invocation so the user can test.

## Ready-for-human notifications

When a dependency changes from blocking to unblocked, re-query its labels and status. If it is open and labeled `ready-for-human`, notify the user prominently with the issue number, title, why it is now unblocked, and the issues it enables. Do not pick it up, relabel it as ready-for-agent, or assign it.

When a human-decision prerequisite is identified, nominate or create a separate human-owned issue only after approval, add the native blocking relationship, and pause the implementation issue. Record the exact decision and artifact that unblocks it.

## Resume and completion

- Require the exact run ID. Load and validate `state.json`; reconcile GitHub state before continuing so existing PRs or branches are not duplicated.
- Recompute only affected dependency readiness after user testing or external changes. Preserve approved model choices unless the user changes them.
- Pause an issue on failure, persistent test failure, missing access, underspecification, or merge conflict. Preserve its worktree and diagnostics. Never auto-rebase or resolve semantic conflicts.
- Before resuming, inspect both local and remote `agent/issue-*` branches and open PRs; skip and report existing work rather than duplicating it.
- When no executable work remains, classify the run explicitly as `completed`, `paused_waiting_for_human`, or `blocked`, retain Markdown/JSON artifacts indefinitely, and report the reason. Remove successful/completed worktrees automatically; retain paused or failed worktrees. Report blocked `ready-for-human` issues and all remaining blockers.

## State shape

`state.json` is authoritative and should include: schema version, repository, milestone, run ID, timestamps, approval history, issue records, native dependency edges with direction defined as `blocked_issue -> blocker_issue`, refinement proposals and approvals, blocker classifications, wave assignments, per-role model recommendations, worktree paths, branch names, subagent reports, test results, PR URLs, status transitions, blockers, resume conditions, final run status, and ready-for-human notifications.
